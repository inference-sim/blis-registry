    Acceptance profiles¶

    How far speculative decoding advances a request per verification step, by model, speculative method, K and thinking mode. Generated at build time from acceptance/, at revision [`96bead697172`](https://github.com/inference-sim/blis-registry/tree/96bead697172ab7f2cf8346e04e65b837014d867); nothing below is typed in by hand.

    An acceptance-profile set is the acceptance counterpart of a coefficient set. Its format, and how a run resolves one value from it, are blis-schemas' acceptance reference (blis-schemas#65). Each profile holds the mean acceptance length (AL): the tokens a request gains per verification step, counting the target's bonus token, so it lies in [1, K + 1]. No per-position rates are stored. A consumer that needs them derives vLLM v0.31.0's minimum-variance schedule, which is how the InferenceX runs that force a published AL realise it.

    inferencex-golden-al¶

    SemiAnalysis InferenceX's golden SPEED-Bench curves, the values its AgentX runs force through vLLM's synthetic_acceptance_length. A cell links to its profile in the file. A dot (·) is a K with no profile, and a lookup for it is refused rather than interpolated.

    Caveats¶

    The set's own caveats, as committed:

    • Coding only. Every profile is SPEED-Bench's coding category, the only one InferenceX publishes; no other category has a value. A consumer must refuse other traffic, or fall back to coding with the substitution recorded; it must not substitute silently.
    • Measured on b300: deepseek-v4-pro, glm-5.2-fp8, glm-5.3, minimax-m3. Acceptance depends mostly on the model, drafter and workload rather than the chip; a resolution on another part records the reuse.
    • Measured on b200: deepseek-v4.1-flash. Acceptance depends mostly on the model, drafter and workload rather than the chip; a resolution on another part records the reuse.
    • deepseek-v4.1-flash dspark: the source file names no hardware. b200 is the part run 34493175056 ran on: its collect-al job 102924945774 ran on runner b200-nscale-slurm_00 (label cluster:b200-nscale) and launched runners/launch_b200-nscale-compat.sh with BENCH_BASE benchmarks/single_node/dsv41flash_fp4_b200.
    • deepseek-v4.1-flash with dspark at K 6-8 was rejected by the image vllm/vllm-openai:deepseekv41-flash-0909 (https://github.com/SemiAnalysisAI/InferenceX/actions/runs/34494319147), so those K have no value.
    • glm-5.3 mtp (K 3) is provisional: copied from glm5.2_mtp.yaml, not measured on glm-5.3.
    • Deployment precision. The fp4 in the collectors' names is the label speedbench-al.yml gives every collection (PRECISION fp4, and the _fp4_b300_vllm.sh name it requires), not the precision served. Each collector serves its model's checkpoint at that checkpoint's own weight precision, which is the catalog model's. At InferenceX 9fa76586ed1e: dsv4_fp4_b300_vllm.sh (deepseek-v4-pro) serves the staged checkpoint with no quantization flag, and --kv-cache-dtype fp8 (line 123); glm52_fp4_b300_vllm.sh (glm-5.2-fp8) serves the staged checkpoint with no quantization flag, and --kv-cache-dtype fp8 (line 131); minimaxm3_fp4_b300_vllm.sh (minimax-m3) serves the staged checkpoint, which its comment (lines 16-19) states is unquantized BF16, with no --kv-cache-dtype. kv_cache_dtype is recorded where a collector sets it; a collector may have changed since its run.
    • The source files for deepseek-v4-pro, glm-5.2-fp8, minimax-m3 name no engine image, so their engine_image reads "unrecorded: the source file names no engine image".
    • Not carried: dsv4-pro-0813-dspark.yaml (deepseek-v4-pro-0813), because its model deepseek-v4-pro-0813 is no catalog model's repository, and no alias maps it.
    • Not carried: kimik3_dspark.yaml (kimi-k3), because the two Kimi-K3 DSpark curves differ only in the draft sampler (greedy, and probabilistic with block rejection), which a profile's key cannot state, and InferenceX's own resolver (curves.py curve_name) refuses to pick one without it.
    • Not carried: kimik3_dspark_probabilistic_sample_method_block_rejection_sample_method.yaml (kimi-k3), because the two Kimi-K3 DSpark curves differ only in the draft sampler (greedy, and probabilistic with block rejection), which a profile's key cannot state, and InferenceX's own resolver (curves.py curve_name) refuses to pick one without it.
    • Not carried: minimaxm3_eagle3_gqa.yaml (minimax-m3), because it is the curve for the Inferact/MiniMax-M3-EAGLE3-GQA drafter and shares minimaxm3_eagle3's key, since a profile's key cannot state the drafter; InferenceX's resolver uses it only for a GQA drafter, and the base curve otherwise.
    • Not carried: qwen3.5_mtp.yaml (qwen3.5-397b-a17b-nvfp4), because its model qwen3.5-397b-a17b-nvfp4 is no catalog model's repository, and no alias maps it.
    • Not carried: qwen3.8next_mtp.yaml (qwen3.8-flash-next-fp8), because its model qwen3.8-flash-next-fp8 is no catalog model's repository, and no alias maps it.

    How the set is made¶

    scripts/emit_acceptance_profiles.py writes the file, and its --check is the drift gate, as for the coefficient writers. The rules it follows are in methodology §12.
